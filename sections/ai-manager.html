AI & Screening

AI Manager

Navigation FT AML → AI Manager

Assists analysts by automating the repetitive first pass through an alert or case, so human review time goes toward judgement calls rather than data-gathering. Configured through two tabs on this same page — Prompt Config (what it's instructed to do) and Model Config (which model it calls) — with alerts also routable into cases automatically via Automation, a separate module.

What It Does

Rather than an analyst manually pulling together a customer's screening history, transaction pattern, and prior case notes before forming a view, AI Manager pre-assembles that context and drafts a preliminary summary — the starting point for the analyst's own review, not a replacement for it.

  • Pulls together the relevant screening hits, transaction history, and prior cases for the subject of a new alert
  • Drafts a preliminary summary of what looks unusual and why, for the analyst to confirm, edit, or reject
  • Flags patterns worth a closer look — e.g. a customer with several recent low-scoring alerts that, taken together, may be more significant than any single one
  • Reduces time spent on repetitive data-gathering so analysts can focus on judgement and disposition

Where Human Review Still Applies

Every output from AI Manager is a draft, not a decision. The Case Lifecycle in Case Manager still applies in full — an analyst reviews the AI-drafted findings, corrects anything wrong, and is the one who selects the final disposition. Nothing AI Manager produces is filed, closed, or escalated without that human sign-off.

Prompt Config

Navigation Homepage → FT AML → AI Manager → Prompt Config

Defines the actual instructions given to the model registered in Model Config — the other half of what makes AI Manager's drafting work. Most prompts are built around a specific purpose, like summarizing a transaction monitoring alert versus a name screening alert — but one prompt, Case Copilot, is different: it's the shared persona and formatting rules used underneath every copilot intent, rather than a summary for one alert type.

Each prompt is shown as its own card: the Purpose as the title, a Status (Active), its current version, when it was last published, and how many revisions it's been through — plus a plain-language description of what the prompt does underneath.

How to use

  • Click Prompt Config in the top right of AI Manager
  • Scan each card's Status and version badge to confirm which prompt is Active and what revision it's on
  • Click a card (or its chevron) to open the full prompt read-only, or click Edit from there to change it

Editing a prompt

Every prompt is built from three parts: Description (what the purpose is for), Task (one instruction — the specific thing to do each run), and Role (the persona and rules the model follows throughout). Editing always shows exactly which version you're changing and what publishing will produce — an explicit "Editing from vX · publishing creates vX+1" banner, so it's never ambiguous whether a save overwrites history or adds to it. It never overwrites: publishing always creates the next version, keeping every prior revision intact.

Version history

The read-only view carries a version stepper at the top — back/forward arrows plus a dropdown that lists every past version by number and publish date, with a search box to jump straight to a specific one (e.g. "7"). This is a full history, not just current-vs-previous: every version a prompt has ever had stays reachable.

Expected Response

Below Role, a prompt can define Expected Response — the structured fields the model's output must fill in, rather than free-form text. Each field lists its name, a type badge where relevant (list), and guidance on what belongs in it; a field can also be an enum — a fixed set of options the model must choose from, such as Case Copilot's own sections/title/items contract, or the Transaction Monitoring prompt's 8-field response with a verdict that must be one of suspicious_activity, expected_behavior, inconclusive, or insufficient_data.

NoteExpected Response is what keeps every copilot output structured and predictable — Case Manager and Alert Manager can render the AI's findings consistently because they know in advance exactly which fields to expect.

Model Config

Navigation Homepage → FT AML → AI Manager → Model Config

Registers the AI model identity AI Manager actually calls — e.g. openai/gpt-oss-120b — together with its API key, version, and Temperature (how deterministic versus varied its output is). Only one configuration is Active at a time.

The API key field is write-only by design — once saved, it's stored encrypted and can never be viewed again through the interface, only replaced via Edit model. Every past configuration is kept below under Previous configurations, each showing its own version, status, temperature, and publish date.

How to use

  • Click Model Config in the top right of AI Manager
  • Click Edit model to change the model identity, API key, version, or Temperature
  • Saving replaces the Active configuration — the one it replaces automatically drops into Previous configurations as Inactive
  • Click Restore on any previous configuration to make it Active again, without having to re-enter its details from scratch
NoteRestoring a previous configuration doesn't reveal its old API key — that stays encrypted the same way it would for a brand new entry, so restoring still requires the key to be valid and current.
